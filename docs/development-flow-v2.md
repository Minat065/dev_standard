# 開発フロー v2（検証容量を中心に再設計）

## v1からの変更点

| 論点 | v1 | v2 |
|---|---|---|
| ボトルネックの定義 | 人間の理解とレビューの帯域 | 検証容量。機械検証・テレメトリ・人間の理解の合計。人間の理解は最も希少な資源として、欠陥コストの厚い尾にだけ割り当てる |
| 人間レビューの適用範囲 | 全PR（軽／重の2段階） | 3レーン。未読レーンは人間が読まない |
| 参照点 | CLAUDE.md と spec.md の2層 | CLAUDE.md（作り方）／INVARIANTS（守るべきこと）／spec（今回作るもの）の3層。不変条件を独立させ、外部規範と自社差分を分けて書く |
| 関門の位置 | PRレベル（CI）とレビュー | エージェントの行動レベル（ハーネス）を追加。PRレベルは最後の砦 |
| 生成と検証の独立 | 仕様を参照点にする | 仕様に加え、検証者を別コンテキスト・別権限のサブエージェントに分離し、決定論的検査（hooks）を挟む |
| WIP制限 | 未レビューPR2件 | 理解容量に対する絞り弁として再定義。止める決定の所有者を明示 |
| 学習 | 「説明できるか」関門 | 理解負債の台帳と、読解が能力になる3条件（生成・帰属・縁の負荷）を構造に組み込む |
| フローの寿命 | 関門を強くし続ける | 関門を強くしつつ、人間読解ゾーンを縮小する昇格・降格基準を持つ |

---

## 基本思想

このフローは4つの前提の上に成り立つ。

第一に、ボトルネックはコード生成ではなく検証容量である。検証容量は機械検証、テレメトリ、人間の理解の合計であり、このうち人間の理解だけが増やしにくい。したがって人間の理解は全コードに均等に配るのではなく、欠陥コストの分布が厚い尾を持つ領域（課金・認証・データ削除・状態遷移・外部連携）に集中させ、それ以外は機械検証とテレメトリで担保する。

第二に、品質は仕組みで担保する。関門は2段ある。エージェントの一手ごとに決定論的に効く関門（ハーネス）と、PRごとに効く関門（CI）である。前者はフィードバックが数秒で返り、後者は数分から数十分かかる。効かせられるものはすべてハーネスへ移し、CIはハーネスをすり抜けたものを止める最後の砦とする。

第三に、生成するAIと検証するAIは相関した失敗をする。同じセッションで実装・レビュー・テストを行わせても独立検証にならない。独立性は3つの手段で作る。人間が書いた参照点（不変条件・仕様）、実装の履歴を見ない別コンテキストの検証者、そしてモデルの解釈に依存しない決定論的検査である。

第四に、人間の理解は消費するだけでなく生産する。エージェントの出力を読む行為が能力になるのは、読む前に不変条件やテストを自分で書き（生成）、見落としが自分の判断に帰属され（帰属）、読む対象が自分の能力の縁にある（縁の負荷）場合に限られる。この3条件を満たさない反復は承認速度だけを上げ、理解速度を上げない。フローはこの3条件を構造として満たす。

守るべき運用ルールは4つ。

1. **不変条件は人間が承認する。** エージェントに下書きさせてよいが、なぜその制約が存在するかを説明して承認する責任は人間にある。
2. **仕様レーンと不変条件レーンでは、自分の言葉で説明できないコードをPRに出さない。** 未読レーンにはこのルールを適用しない。代わりに不変条件の機械検査、フィーチャーフラグ、テレメトリが担保する。
3. **理解容量を超えたら生成を止める。** 未レビューPRが上限に達したら、仕様レーンと不変条件レーンの生成を停止する。上限を上げる決定はリーダーが理解負債台帳を見て行い、エンジニア個人に押し付けない。
4. **レビュー時間の短縮を指標にしない。** それは厳密さの低下で最も安く達成できる。

## Layer 0：ハーネス（エージェントの行動レベルの関門）

v1にはこの層がなかった。Claude Codeを「実装者」として扱うなら、実装者が働く環境そのものが関門になる。ハーネスとは、CLAUDE.md、settings.json、hooks、サブエージェント定義、skills、MCP接続、ヘッドレス実行の総体を指す。

### CLAUDE.md（作り方の規約）

短く、実行可能な規則だけを書く。build／test／lint のコマンド、禁止API、依存追加のルール、リポジトリ固有で自明でない規約。リポジトリの概説、設計思想の説明、READMEの再掲は書かない。コンテキストファイルは平均ではタスク成功率を改善せず推論コストを20%以上増やすという2026年の測定があり、価値があるのはエージェントが自力で推測できない非標準の規則に限られる。settings.json や hooks で強制できるものは CLAUDE.md に書かず、設定として強制する。プロンプトは解釈されるが、設定は解釈されない。

### settings.json（権限）

プロジェクトの `.claude/settings.json` をコミットし、チーム全員のエージェントに同じ権限境界を適用する。deny リストに本番の資格情報、破壊的コマンド、secretsを含むパス、社内ネットワークへの WebFetch を入れる。permission mode はレーンで変える。未読レーンの定型作業はプロンプトなしで進める設定、不変条件レーンは編集ごとに確認する設定にする。エージェントに与える権限は「そのレーンで壊してよい範囲」と一致させる。

### hooks（決定論的検査）

hooks はモデルの解釈に依存せず、イベントに応じてスクリプトを実行し、終了コードで行動をブロックできる。v1のPhase 2「保存時に自動実行」とPhase 3「機械の関門」の一部をここへ移す。

| イベント | 用途 |
|---|---|
| SessionStart | 現在の issue、spec、関連する INVARIANTS の該当節をコンテキストへ注入する。エージェントに探させない |
| PreToolUse（Bash） | 危険コマンド、secrets の読み取り、本番向け操作をブロックする |
| PostToolUse（Edit／Write） | フォーマッタ、Linter、型チェックを即時実行し、失敗をエージェントに返す。人間が書式を見ることを構造的に不可能にする |
| Stop | 変更があればテストを実行し、失敗していればセッションを終了させない。テストを通さずに「完了」と報告する経路を塞ぐ |
| SubagentStop | 検証サブエージェントの出力形式を検査する |
| PreCompact | コンパクト前に作業状態をファイルへ書き出させる |

### サブエージェント（検証の独立性）

`.claude/agents/` に3種類を定義し、ツールと権限を分ける。

- **explore**：読み取り専用、廉価モデル。コードベース探索を担い、主コンテキストへは要約だけを返す。長いコンテキストは入力長そのものが推論性能を落とすため、探索と判断を同じコンテキストで行わない。
- **spec-tester**：spec と INVARIANTS のみを読み、実装コードを読まずにテストを書く。編集権限はテストディレクトリに限定する。実装を見せないことで、実装をなぞるだけのテストを構造的に防ぐ。
- **reviewer**：diff、spec、INVARIANTS を入力とし、実装セッションの履歴を見ない。編集権限なし。上位モデル。指摘はカテゴリ別（境界値、エラー経路、認可、並行、互換性、不変条件違反、テスト不足）に出す。

### skills（手順の固定化）

`/spec`（issue から EARS 形式の受入条件と Out of scope を起こす）、`/slice`（spec を縦スライスに刻みレーンを提案する）、`/self-review`（PR前の自己点検）、`/pr`（目的・変更点・確認方法・参照する spec と INVARIANTS の条項を含む説明文を生成する）を skill として置く。手順をプロンプトとして毎回書かせない。

### コンテキスト衛生

1スライス1セッション。スライスが終わったらセッションを閉じ、次のスライスは新しいセッションで始める。巨大セッションを継続しない。実装前に plan mode で計画を出させ、不変条件レーンでは計画を人間が承認してから編集を許可する。

### ヘッドレス実行（CI側）

AI一次レビューと「CI失敗を修正させるループ」はヘッドレスで走らせる。修正ループには回数上限を置き、上限到達で人間へ返す。

## Phase 0：参照点（3層）

**CLAUDE.md** はハーネスの節で述べた。

**INVARIANTS**（リポジトリ直下、機能横断）に「守るべきこと」を書く。2つの部分に分ける。外部規範の参照（決済の状態遷移規則、会計基準、業界標準、法規制など、自社の外で定義されている制約）と、自社差分（自社が外部規範に加えている、または意図的に逸脱している制約）。それぞれの条項には理由を書く。可能な限り機械可読へ落とす。状態遷移は状態機械テストへ、数量制約は property-based test へ、型で表現できる制約は型へ。機械可読に落とせない条項は不変条件レーンのレビュー観点として残る。

INVARIANTS の執筆は若手に割り当て、ドメイン専門家とシニアが承認する。不変条件を書くには「なぜその制約があるか」を問わなければ書けず、書かれたものは可視で批評可能である。これが暗黙知の継承経路になる。

**spec.md** は機能ごとに書く。1〜3ページ、受入条件は EARS 形式、Out of scope を明記する。加えて、参照する INVARIANTS の条項番号と、各受入条件のレーンを書く。

## Phase 1：分割とレーン割当

仕様を受入条件1〜2個＝1 issue＝1 PR に刻む。縦（機能スライス）で切る。各 issue は spec と INVARIANTS の条項を参照する。

各スライスにレーンを割り当てる。判定基準は欠陥コストの分布である。

| レーン | 条件 | 人間の関与 | マージ条件 |
|---|---|---|---|
| **未読** | 欠陥コストが有界（表示、社内ツール、ログ、テストコード、ドキュメント）、フィーチャーフラグで戻せる、テレメトリで欠陥を検出できる | 読まない | ハーネス通過、CI通過、AIレビュー通過、フラグOFFでデプロイ、監視設定済み |
| **仕様** | 外部から観測できる振る舞いの変更で、INVARIANTS の条項に触れない | 1人が spec と diff を照合する | 上記＋人間approve |
| **不変条件** | INVARIANTS の条項に触れる。課金、認証、データ削除、状態遷移、外部連携 | 人間が先に不変条件の該当条項を確認し、失敗するテストを承認してから実装させる。深い読解 | 上記＋不変条件テストの通過＋予測付きレビュー |

レーンの判定に迷ったら上のレーンへ寄せる。判定を間違えて欠陥が出た場合は Phase 6 で昇格する。

**絞り弁。** 仕様レーンと不変条件レーンの未レビューPRに上限を置く（初期値2）。上限到達時、未読レーンの生成は継続してよいが、他の2レーンの生成は停止する。エージェントは並列にいくらでも生成できるため、この停止は自動で起きない。誰が止めるかを決めておく。上限を上げる決定は、理解負債台帳（後述）の予測命中率と逃し欠陥件数を見てリーダーが行う。

## Phase 2：実装

実装セッションは SessionStart hook が注入した issue、spec、INVARIANTS の該当節を文脈として開始する。

不変条件レーンでは、実装前に spec-tester サブエージェントが spec と INVARIANTS から失敗するテストを書き、人間が承認する。人間が自分で書いてもよい。この工程が「生成」の側の学習を担保し、同時にレビューの錨になる。仕様に対して diff を読むのと、diff だけを読んで正しさを推測するのでは、後者の方が検出率も学習効率も低い。

実装中は PostToolUse hook が書式・Linter・型を返し、Stop hook がテストを通さないセッション終了を止める。

PR を出す前の自己関門は2つ。仕様レーンと不変条件レーンでは、自分の言葉で説明できること、セルフレビューをしたこと。未読レーンでは PR 説明文をエージェントに生成させ、人間は読まない。説明文には目的、変更点、確認方法、参照条項、変更していないもの、実行した検証を含める。

---

## Phase 3：機械の関門とAI一次レビュー

CI で format／lint／型チェック、自動テスト（過去障害の再現テストを含む）、依存の脆弱性スキャン、INVARIANTS から落とした状態機械テストと property test を実行する。落ちたらマージできない。ハーネスで既に通っているはずのものが CI で落ちた場合、それはハーネスの穴として Phase 6 に記録する。

AI一次レビューは reviewer サブエージェントをヘッドレスで走らせる。入力は diff、spec、INVARIANTS。実装セッションの履歴は渡さない。出力は作者側が先に消化し、人間レビュアーには AI の全指摘ではなく、最終 diff、説明文、残存リスクを見せる。レビュアーに AI の修正候補まで見せると review 時間が5%以上増えたという測定があり、作者側で消化してレビュアー側では畳むと回帰が消えた。

---

## Phase 4：人間の関門（レーン別）

**未読レーン**：人間の関門はない。機械の関門とフラグと監視が承認である。

**仕様レーン**：1人が spec の受入条件と diff を照合する。設計の一貫性と、テストが実装をなぞっているだけでないかを見る。

**不変条件レーン**：読む前に、この変更がどこで壊れうるかの予測をレビューコメントに書く。読んでから予測と照合する。「なぜこうしたのか」を1つ聞き、答えられなければ差し戻す。予測の当否を理解負債台帳に記録する。予測が当たり続けるモジュールは理解負債が返済されており、外れ続けるモジュールは読解の対象として正しい。

---

## Phase 5：リリース

v1と同じ順序で行う。成果物の固定、互換を保ったマイグレーション、staging で EARS 条件の確認、フラグ OFF でデプロイ、段階的公開、事前文書化されたロールバック。

v2で追加する条件は2つ。未読レーンの変更はフラグ必須とし、フラグなしでは未読レーンに入れない。不変条件レーンの変更は、staging で INVARIANTS の該当条項を実環境で確認する。

---

## Phase 6：運用と学習ループ

エラー通知、ログ、監視を置く。未読レーンが成立する前提はここにあり、テレメトリのないモジュールに未読レーンを適用してはならない。

障害が起きたらポストモーテムを行う。問うのは「なぜ手前の関門で気づけなかったか」に加えて、次の帰属である。

- どのレーンだったか。レーン判定は正しかったか。
- どの関門（ハーネス／CI／AIレビュー／人間レビュー）で止まるべきだったか。
- INVARIANTS のどの条項に触れていたか。条項がなかったなら追記する。
- 不変条件レーンなら、レビューの予測は何を見落としたか。

関門の強化は上流から順に行う。ハーネス（hook や deny の追加）で止められるならそこで止める。次に CI、次に INVARIANTS の機械可読化、次に spec の受入条件、最後にレビュー観点。人間の注意に頼る対策は最後の選択肢である。

**レーンの昇格と降格。** 不変条件レーンのモジュールが、該当する不変条件をすべて機械検査化し、直近 N リリースで逃し欠陥ゼロなら仕様レーンへ降格させる。仕様レーンのモジュールが、テレメトリで欠陥を検出でき、フラグで戻せ、直近 N リリースで逃し欠陥ゼロなら未読レーンへ降格させる。逆に、未読レーンで逃し欠陥が出たら仕様レーンへ昇格させる。この規則によって、フローは自分の人間読解ゾーンを縮小させる。縮小しきらない残余、すなわち外部規範同士の衝突の裁定、規範を意図的に破る判断、見落としの言語化が、人間の仕事として残る。

## 理解負債の台帳

| 指標 | 意味 | 望ましい方向 |
|---|---|---|
| 予測命中率（モジュール別） | 不変条件レーンで、読む前の予測が読んだ後に当たった比率 | 上昇。承認速度と理解速度を区別する唯一の指標 |
| 逃し欠陥件数（レーン別） | 本番で見つかった欠陥のうち、各レーンを通過したもの | 減少。未読レーンで増えたらレーン判定を見直す |
| 未読レーン比率 | 全PRのうち未読レーンの比率 | 逃し欠陥が増えない範囲での上昇 |
| レビュー待ち時間 | 仕様・不変条件レーンPRの未レビュー滞留 | 絞り弁の信号として使う。評価指標にしない |
| 関門別の捕捉件数 | ハーネス／CI／AIレビュー／人間レビューのどこで欠陥が止まったか | 上流へ移動 |

使わない指標：レビュー時間、AI生成行数、PR数、エージェント利用率。

## 導入順序

全部を一度に入れない。効果が見えやすく反発が起きにくい順に：

1. フォーマッタ・Linter
2. CI
3. ハーネスの最小構成（settings.json の deny リスト、PostToolUse hook でフォーマッタ・Linter・型）
4. CLAUDE.md（コマンドと禁止事項だけ）
5. バグ修正時の再現テスト
6. INVARIANTS（これから触る場所から、外部規範の参照と自社差分を書く）
7. PRテンプレートと spec の受入条件、レーン欄
8. reviewer サブエージェントとヘッドレス一次レビュー
9. spec-tester サブエージェントと不変条件レーンの先行テスト
10. レーン制の運用開始と理解負債台帳
11. リリース手順のチェックリスト化

既存コード全体に遡って適用はせず、「これから触る場所だけ基準を上げる」ルールで運用する。レーン制の運用開始時点では、判定に迷うものをすべて仕様レーンに入れ、未読レーンは台帳が動いてから開く。
